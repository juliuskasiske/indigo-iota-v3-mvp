1 · From word to coordinate

The foundational idea: every word (and every fragment of a word) maps to a point in a high-dimensional space. The position encodes meaning. Words that mean similar things live near each other; unrelated words live far apart.

In two dimensions you can draw it: 

        ▲
        │                        "monarch"
        │  "democracy"              ●
        │      ●
        │
        │                                   "dog"
        │                                    ●
        │              "cat"
        │               ●
        │
        └────────────────────────────────────────────▶
           political ◀──────────────────▶ biological
A toy 2-D embedding space — 2 axes, human-labelled for clarity. jina-v3 uses 1 024 axes, none of which are human-labelled.

jina-v3 uses 1 024 dimensions. You cannot draw it, but the geometry is identical — closeness = similarity, direction = meaning, arithmetic works (king − man + woman ≈ queen).

Every word-piece in jina-v3's vocabulary has a fixed starting coordinate stored in a giant lookup table: 

  VOCABULARY TABLE   250 002 rows × 1 024 columns
  ┌────────────────┬──────────────────────────────────────────────────────────┐
  │  Token ID      │  Coordinate vector (1 024 numbers)                       │
  ├────────────────┼──────────────────────────────────────────────────────────┤
  │     4 312      │  [ 0.14, −0.83,  0.22,  0.61, … (1 020 more) …  −0.19 ] │
  │     8 891      │  [ 0.91,  0.04, −0.55,  0.18, … (1 020 more) …   0.73 ] │
  │    12 044      │  [ −0.33, 0.67,  0.11, −0.90, … (1 020 more) …   0.05 ] │
  │       …        │                     …                                     │
  └────────────────┴──────────────────────────────────────────────────────────┘

  RAM cost: 250 002 × 1 024 × 4 bytes (float32) = 1 024 MB ≈ 1 GB
The token embedding table — the first major RAM consumer.

2 · The fundamental problem — context

The lookup table gives every token a fixed coordinate. That breaks immediately:

  Sentence A:  "I walked along the river  bank  at sunset."
  Sentence B:  "She deposited cash at the bank  before closing."

  After lookup table:
    "bank" in A  →  [ 0.61, −0.55, 0.18, … ]   ← identical
    "bank" in B  →  [ 0.61, −0.55, 0.18, … ]   ← identical

  But they mean completely different things.
A static lookup table cannot represent context-dependent meaning.

This is the problem the transformer was invented to solve. Its job is to update each token's coordinate by looking at the surrounding tokens, so that by the end of the network "bank" in sentence A has a different coordinate than "bank" in sentence B.

3 · Tokens — what the model actually sees

The model does not see words. It sees tokens — chunks produced by a subword tokeniser. Short common words are one token; rare or compound words split into pieces. This lets the vocabulary stay bounded at 250 K entries while handling any language. 

  Input:   "Transformers sind mächtig."

  Tokens:  ["Trans", "##form", "##ers", "sind", "mäch", "##tig", "."]
             ↓         ↓         ↓        ↓       ↓       ↓       ↓
  IDs:    [12044,   8891,    4312,   31002,  58821,  9034,   119  ]

  Each ID → one row from the vocabulary table → one 1 024-number vector.
Subword tokenisation. "##" marks a continuation piece. German text tokenises naturally because jina-v3's vocabulary was trained on 100+ languages.
Tokens are like syllables in a spoken word — "trans·form·ers". You don't need a separate dictionary entry for every compound; you build them from pieces you already know.

4 · The residual stream — a shared whiteboard

Imagine a whiteboard with one column per token. Each column holds 1 024 numbers — the model's current best understanding of that token. 

  Tokens:    "I"       "went"    "to"      "bank"    "."
             ──────    ──────    ──────    ──────    ──────
  Dim  1:    0.14     −0.23      0.88      0.61     −0.44
  Dim  2:   −0.83      0.71     −0.12     −0.55      0.92
  Dim  3:    0.22     −0.44      0.33      0.18      0.07
    …          …         …         …         …         …
  Dim 1024:  0.61      0.08     −0.91      0.73     −0.28

             ◀── 5 columns × 1 024 rows = 5 120 numbers total ──▶
The residual stream after the embedding lookup. All columns start as static dictionary values. The transformer's job is to rewrite them.

This whiteboard is called the residual stream. Each of the 24 transformer layers adds small corrections to it — it never replaces the whole thing, only adjusts it. By layer 24, every column reflects not just the token itself but its full context in the sentence.

The residual stream for a 512-token email costs:
512 tokens × 1 024 dims × 4 bytes = 2 MB per copy. Negligible. The RAM problem is elsewhere.

5 · One attention head — step by step

Each transformer layer runs self-attention: every token gets to look at every other token and decide how much to borrow from it. There are three learned weight matrices — Q, K, and V — each of size 1 024 × 64 (one head's share of the 1 024 hidden dims).

1

Project every token into three 64-number vectors

  "bank" column (1 024 numbers)
      × Q matrix (1 024 × 64)  →  query  q  (64 numbers) — "what am I looking for?"
      × K matrix (1 024 × 64)  →  key    k  (64 numbers) — "what do I contain?"
      × V matrix (1 024 × 64)  →  value  v  (64 numbers) — "what should I share?"

Every token generates its own q, k, and v. That's 3 projections × 5 tokens = 15 small vectors for a 5-token sentence.

2

Score every other token against "bank"'s question

  score("bank" → "river")   = dot_product(q_bank, k_river)   / √64  =  8.4
  score("bank" → "went")    = dot_product(q_bank, k_went)    / √64  =  2.1
  score("bank" → "to")      = dot_product(q_bank, k_to)      / √64  =  1.0
  score("bank" → "I")       = dot_product(q_bank, k_I)       / √64  =  0.9
  score("bank" → ".")       = dot_product(q_bank, k_dot)     / √64  =  0.5

  The √64 (= 8) prevents the numbers from growing so large that softmax
  pushes all weight onto one token and ignores the rest.
3

Softmax — turn raw scores into a probability distribution

  Sentence A:  "I went to the river bank."

  "bank" pays attention to:
    "river"  ██████████████████████████████████  62 %   ← geography signal
    "went"   ████████                            18 %
    "to"     ████                                 8 %
    "I"      ███                                  7 %
    "."      ██                                   5 %

  —————————————————————————————————————————————————————

  Sentence B:  "She deposited cash at the bank."

  "bank" pays attention to:
    "deposited"  ██████████████████████████████████  68 %   ← finance signal
    "cash"       █████████████                       24 %
    "at"         ██                                   5 %
    "the"        █                                    2 %
    "."          ▏                                    1 %

  Same token, completely different attention pattern.
4

Pull value vectors, weighted by attention — then add to the whiteboard

  new_info_for_bank =
      0.62 × v_river
    + 0.18 × v_went
    + 0.08 × v_to
    + 0.07 × v_I
    + 0.05 × v_dot

  This produces a 64-number vector. It gets ADDED back to "bank"'s
  column on the residual stream whiteboard — adjusting it, not replacing it.

After this update, "bank" in sentence A has absorbed meaning from "river". Its column on the whiteboard now points toward the geographical region of vector space. In sentence B it absorbed "deposited" and "cash" instead, pointing toward finance.

6 · 16 heads per layer — what each one looks for

One head gives one 64-number slice of context. jina-v3 runs 16 heads simultaneously per layer, each with independent Q/K/V matrices. They learn to attend to different structural patterns: 

  HEAD   DIMS    WHAT IT TENDS TO LEARN (emergent, not programmed)
  ─────  ──────  ──────────────────────────────────────────────────────────────
   1     0– 63   Grammatical role — subject, verb, object dependencies
   2    64–127   Coreference — "he" links back to "Johannes" three words earlier
   3   128–191   Sentence position — early vs late, before/after a comma
   4   192–255   Named-entity type — person name, place, organisation, date
   5   256–319   Negation scope — the reach of "not", "kein", "never"
   6   320–383   Syntactic head — which word governs a prepositional phrase
   7   384–447   Semantic field — body-of-water words cluster together
   8   448–511   Cross-lingual alignment — "Geld" and "money" occupy same slot
   …      …      …
  16   960–1023  (Something the network found useful; not interpretable)
These specialisations emerge from training — they are never explicitly programmed. Each head independently runs the four steps above.

All 16 outputs (16 × 64 = 1 024 numbers) are concatenated and passed through a final output projection matrix (1 024 × 1 024) that blends them back into the shared residual stream. The whiteboard column stays 1 024-wide — same shape in, same shape out.

RAM cost of one attention layer

  Per head:           Q: 1024×64,  K: 1024×64,  V: 1024×64
  16 heads:           3 matrices × 16 × 1024 × 64  =  3 145 728 params
  Output projection:  1024 × 1024                  =  1 048 576 params
  ─────────────────────────────────────────────────────────────────────
  Total per layer:    ~4 194 304 params  =  4 M params  × 4 B  =  16 MB (float32)

7 · The feed-forward block — per-token pattern matching

After attention shares information across tokens, each token's column passes through a two-layer MLP independently. No cross-token communication here — it's the same network applied to each column in isolation. 

  "bank" column (1 024 numbers)
       ↓
  Expand:   × W₁  (1 024 × 4 096)  →  4 096 numbers    ← 4× wider
       ↓
  Activate: GELU non-linearity       →  4 096 numbers    ← kills negative activations
       ↓
  Compress: × W₂  (4 096 × 1 024)  →  1 024 numbers    ← back to stream width
       ↓
  Added to the residual stream (just like attention output)
The FFN expand–activate–compress pattern. The 4× expansion (1 024 → 4 096 → 1 024) is where factual associations are thought to be stored — "Paris" → "capital" → "France".

RAM cost of one FFN layer

  W₁:  1 024 × 4 096  =  4 194 304 params  →  16 MB (float32)
  W₂:  4 096 × 1 024  =  4 194 304 params  →  16 MB (float32)
  ─────────────────────────────────────────────────────────────
  Total per layer:    ~8 M params  =  32 MB (float32)

8 · 24 layers — what stacking achieves

The whiteboard gets rewritten 24 times. Attention + FFN = one layer. Each pass adds a new level of abstraction: 

  ┌────────────────────────────────────────────────────────────┐
  │  LAYER  1:  Surface structure — punctuation, word order    │
  │  LAYER  4:  Morphology — verb tenses, plural endings       │
  │  LAYER  8:  Syntactic roles — subject/verb/object arcs     │
  │  LAYER 12:  Named entities — person, organisation, place   │
  │  LAYER 16:  Semantic frames — finance, geography, medicine  │
  │  LAYER 20:  Cross-sentence coherence, discourse structure  │
  │  LAYER 24:  Final contextualised representation            │
  │              ↓                                             │
  │    Each token column now reflects the full sentence.       │
  └────────────────────────────────────────────────────────────┘
Approximate specialisation by depth (from mechanistic interpretability research). Not strict boundaries — representations are distributed across layers.

"Bank" entered layer 1 with the same column in both sentences. It exits layer 24 with a column shaped by everything around it. The two sentences now produce meaningfully different 1 024-number columns for that token.

9 · Pooling — collapsing many columns into one vector

After 24 layers you have one 1 024-number column per token. But you need one vector for the whole input to store in the database and compare with cosine similarity. 

  After layer 24:

  "I"      "went"   "to"     "bank"   "."
  ──────   ──────   ──────   ──────   ──────
   0.21    −0.18    0.74     0.89    −0.31     ← dim 1
  −0.77     0.63   −0.04    −0.22     0.88     ← dim 2
    …         …       …       …       …
  ──────   ──────   ──────   ──────   ──────
      ↓
  MEAN POOLING: average each dimension across all 5 columns
      ↓
  [ (0.21−0.18+0.74+0.89−0.31)/5,  (−0.77+0.63−0.04−0.22+0.88)/5,  … ]
  =  [ 0.27,  0.096,  … ]       ← one 1 024-number vector

  This is the embedding you store in the pgvector column.
  Cosine similarity between two such vectors = semantic relatedness.
Mean pooling — the simplest and most common method. jina-v3 uses a learned pooling variant, but the intuition is the same.
Pooling is like averaging the votes of 512 jury members into a single verdict. Each member (token) has already heard from every other member (via attention) before casting their vote.

Your server saw anon-rss: 7 272 316 kB (≈ 7.2 GB) in the OOM log. Here is exactly where that comes from.

The crash loop multiplied this. With 4 containers dying and restarting in 10-second intervals, each in the ONNX init phase simultaneously, the peak hit 4 × ~2 GB = ~8 GB — exhausting all physical RAM on a 7.6 GB server in seconds.

Note that the user's formula (1 024 × context_tokens) × 16/4/8 was computing activation memory — which is < 50 MB and completely irrelevant. The RAM problem is the model weight storage + ONNX optimisation overhead, which is independent of input length.

11 · Why a smaller model is fine for email classification

jina-v3's size is justified when you need to embed long legal documents (8 192 tokens), compare across 100 languages simultaneously, or serve millions of queries. For "is this email work-relevant?" — a binary classifier over typical emails of 50–300 tokens — the quality difference between a 559 M-param model and a 118 M-param model is not measurable in practice.

Current — jina-v3

jinaai/jina-embeddings-v3

1 024 dimensions

8 192 token context

~3 GB steady-state RAM

~4–7 GB init peak

Overkill for a scope gate classifier. Useful if you need long-document embedding or fine-grained cross-lingual nuance.

Recommended swap

intfloat/multilingual-e5-small

118 M parameters

384 dimensions

512 token context

~300 MB steady-state RAM

~500 MB init peak

Still multilingual (German + English). Still transformer + attention. 10× lighter. Classification accuracy on short emails is indistinguishable.

The switch requires one DB migration (resize the embedding column from 1 024 to 384 dims, recreate the HNSW index) and a one-line change in src/ingestion/index/embeddings.py. Since no successful backfill has run yet, there are no stored embeddings to invalidate — the migration is clean.

Both models have the same architecture: token lookup → residual stream → N × (attention + FFN) → mean pool. The only differences are N (6 layers instead of 24), hidden dimension (384 instead of 1 024), and context window (512 instead of 8 192). Every concept on this page applies to both.

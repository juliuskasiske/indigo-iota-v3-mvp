Chapter 4

Every page, and what you can do on it

The website has twelve screens. Every screenshot below is the real app running on a laptop — not a mock-up of a mock-up. For each one you'll see what it shows, what buttons actually do, and whether it's wired to the live backend or is a polished demo of a feature not yet connected.

One thing to understand first: "live" vs "demo". The app is half real engine, half showroom. Five screens talk to the real backend and the real database — Admin, Ask, the owner-only Control Tower, and the two sign-in screens people reach from an emailed link. The other seven are a convincing demo: they look and behave like the finished product, but their data is hard-coded in the browser and resets on refresh. Each section is tagged so you always know which is which.

How to read the tags

live — this screen sends real HTTP requests to the backend and shows real database data. Changes stick.
demo — this screen runs entirely in the browser from canned data (frontend/src/lib/mock/data.ts). It's for showing the intended experience; nothing is saved.

Think of a show home. The kitchen taps run real water (the live pages) — but the fruit bowl on the counter is plastic (the demo pages). Both are there so you can see what living here feels like; only some of it is plumbed in.

Where the data comes from (two wires)

Every page pulls its data down one of two wires. Knowing which wire a page uses tells you instantly whether it's live or demo:

The wireWhat it isFileUsed by
the API client A small set of functions that make real HTTP calls to the backend (me(), ask(), credits()…). frontend/src/lib/api.ts Admin, Ask, Control Tower, accept-invite, reset-password
the demo store An in-browser store of fake projects, seeded from a fixtures file. Lives only in memory. frontend/src/lib/store/projects-store.tsx + lib/mock/data.ts Home, Demo, Projects, New, View, Check-in, Settings

The shell every page sits inside

Before the individual pages: all of them are wrapped in one shared frame called the AppShell (frontend/src/components/app-shell.tsx) — the persistent left sidebar and top strip you see in every screenshot. The actual page just fills the middle. The very outermost wrapper, frontend/src/app/layout.tsx, loads the fonts and the demo store once for the whole site.

1. Home demo route /, file src/app/page.tsx

What it is: the front page you land on after opening the app. It surfaces one featured project (the "LatticePay" demo engagement) with summary tiles and recent activity.

2. Admin Center live route /admin, file src/app/admin/page.tsx

Once onboarded it switches to the steady-state dashboard (admin-dashboard.tsx). Inside step 1 — Objectives live

What it is: where a person tells the system what "better" means. Nothing in the diagnosis layer can run until this is filled in, because every later judgement is made against it.

It is four sections, in order:

  1. The objective function. A list of possible levers — grow revenue, cut cost, improve retention, and so on — which you drag into priority order. Rank one is what the agents weigh most.
  2. The program. The part that makes the goal checkable rather than aspirational: what unit the impact is measured in, whether it recurs every year or happens once, where the company is today, where it must get to, by when, which financial year the run rate is measured in, and how often progress is reviewed. Underneath the fields there is a plain-English read-back of what you have entered — "Grow revenue from €6.2M to €12.4M (2×), recurring run-rate, by 31 Dec 2027, reviewed monthly" — assembled in the browser from the field values, with no AI involved, so the form stays legible while you fill it in.
  3. The objective sentence. One button asks the agents to compress everything above into a single sentence. You can edit it. That sentence becomes the root box of the tree, which is why you approve it before any agent time is spent: a whole diagnosis built on a mis-stated goal is a whole diagnosis wasted. If you change the program afterwards, a small chip appears warning that the sentence is now out of date.
  4. Context. Free text: anything about the company the agents should know but could not have read anywhere.

Under the hood: GET and PUT /api/objective for the fields, POST /api/objective/headline for the sentence. Saving is admin-only; a consultant or viewer sees the same screen read-only with a line explaining why, rather than being allowed to type and then rejected.

Inside Overview — the diagnosis board live

What it is: the diagnosis, drawn the way a consultant would draw it on a wall. The objective sits at the top. Below it the branches fan out, and at the bottom sit the initiatives. Boxes and arrows, top to bottom.

Above the board sit two strips. One says whether a run is in progress and how many boxes exist. The other is the coverage bar: how much value the initiatives add up to against the target, split into the part that is evidenced and the part that is still only claimed. Reading "€575k of €12.4M revenue target, 5% covered" tells you in one line that the work is nowhere near done — which is more useful than a board that merely looks full.

What you can do:

  • Move around. Drag to pan, pinch or hold ⌘ and scroll to zoom, or press the fit-to-view button to bring the whole tree back into frame.
  • Follow the reasoning. Hovering a box lights up the whole path from it back to the objective and dims everything else. That is what turns the picture from decoration into an argument you can read: you can see exactly which chain of reasoning leads to any given initiative.
  • Open a box. Clicking opens a panel at the side. A branch shows why it exists and why its siblings together cover the whole of the parent. An initiative shows all five card fields — what it means, how you would size it, what would need to be true, the immediate next steps, and the evidence behind it. The panel deliberately does not block the board: you can keep clicking around behind it.
  • Argue with it. At the top of that panel are the two review actions — reject the box with a reason, or leave a note asking for it to be reworked. Both send the agents back to that part of the tree. This is covered properly in Chapter 10.

Under the hood: GET /api/swarm/tree returns a flat list of boxes, each naming its parent. The browser turns that list into a picture in steps/tree-layout.ts — about sixty lines of arithmetic with no charting library involved: leaves are stacked one after another, and every parent is then placed at the midpoint of its own children. Below the board is the activity log, a plain feed of what each agent did, newest last.

There is no screenshot of this screen or of Objectives in this guide yet; both are newer than the images above, which were captured before the diagnosis layer existed.

3. Ask live route /ask, file src/app/ask/page.tsx

What it is: the question box over the project brain. You type a natural-language question; the backend retrieves the relevant pieces of the brain, hands them to the AI, and the AI writes an answer that cites its sources.

What you can do: type a question and submit it. You get back prose plus a list of numbered sources you can expand. This is real Retrieval-Augmented Generation against the live tenant database.

Under the hood: calls api.ask(question) → backend route /api/qa/ask. The answer and its sources are real. Chapter 5, flow C follows this request all the way down and back.

4. Projects demo route /projects, file src/app/projects/page.tsx

What it is: a grid of all engagements. What you can do: browse and open one, or start a new one. Under the hood: useProjects() from the demo store — the list lives in the browser only.

5. New project demo route /projects/new, file src/app/projects/new/page.tsx

What it is: a multi-step form for spinning up a new engagement (name it, set scope, pick connectors). What you can do: fill it in and "create" — which adds a project to the in-browser store for the rest of the session. Under the hood: pure demo; in the real product this would drive the onboarding/connector setup described in the data model.

6. Project view demo route /projects/view, file src/app/projects/view/page.tsx

What it is: the "inside one project" view — the visual showcase of what a finished brain looks like: entity cards, a timeline, and a knowledge-graph visual. What you can do: explore the tabs and entities. Under the hood: useProjects() demo data. This is the demo counterpart to the real data you saw on the live Ask page.

7. Check-in demo route /projects/check-in, file src/app/projects/check-in/page.tsx

What it is: a status-digest screen summarising recent movement on an engagement. What you can do: read the summary. Under the hood: demo store; illustrates a planned recurring report.

8. Settings demo route /settings, file src/app/settings/page.tsx

What it is: account / workspace preferences. What you can do: view the intended settings layout. Under the hood: reads allProjects from lib/mock/data.ts; not wired to the backend.

9. Control Tower live route /control, file src/app/control/page.tsx, owner-only

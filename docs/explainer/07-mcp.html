Chapter 7

The MCP server — letting Claude & ChatGPT use the brain

Everything so far assumed a person using the website. This chapter is about the newest doorway into the same brain: a way for an AI assistant — Claude or ChatGPT — to read a customer's brain directly, as a set of tools, on that person's behalf. It's the most security-sensitive thing we built, so we build the idea up slowly and show exactly what each step protects against.

The short version: a customer can paste one URL into Claude/ChatGPT's “connectors” and, after a one-click approval, the assistant can search and ask their brain — scoped to one workspace, read-only, and revocable, without ever handing the assistant a password.

What is MCP, and why do we need it?

MCP (Model Context Protocol) is a small, shared standard for how an AI assistant discovers and calls “tools” on an outside server. Claude and ChatGPT both speak it. If our server exposes the brain as MCP tools, those assistants can use it with no custom integration on either side — the user just adds a “connector” by URL.

Why bother, when we already have an /api/qa/ask on the website? Because the value is letting someone work the brain from inside the assistant they already use — “Claude, what do we know about the ACCHCO project?” — mixing brain facts with everything else Claude can do, instead of switching to our site for every question.

Think of the brain as a reference library. The website is the reading room where a member walks in and looks things up. MCP is a library card you can lend to an assistant: the assistant can fetch from the stacks for you — but only the shelves the card allows, and you can cancel the card at any time.

Two doorways into the same brain

The backend now answers on two different doors, and it's worth keeping them straight:

DoorWho knocksHow they prove who they areCode
/api/*, /auth/* a person in our website the iota_session cookie (Chapter 5) backend/src/api/app.py
/mcp a program (Claude/ChatGPT) a bearer token it attaches to each call backend/src/mcp_server.py

The cookie vs. bearer token split is the whole reason MCP needed new code. A cookie is something a browser sends automatically on our own site. A bearer token is something a program stores and attaches on purpose (Authorization: Bearer …). The brain data and tools underneath are identical; only the doorway and the proof-of-identity differ.

The tools on offer

The MCP server exposes seven read-only tools over each tenant's brain. They all return raw facts (no AI, no cost) — the connector never spends the workspace's LLM credits.

Deliberately, the tools hand the assistant raw chunks + graph context and let it do the reasoning — that's usually better, and it keeps every credit-spending model call on the assistant's side, not the brain's. (There used to be a server-side ask tool that ran the brain's own RAG synthesis; it was removed so a connector can't run up a bill — the product's in-app Ask page still does synthesis when a human asks there.)

The hard part: how does the assistant get in?

We need the assistant to call /mcp with proof of identity. The naïve idea — “give it an API key” — fails three tests at once:

  • The user would have to hand a long-lived secret to a third-party program. If it leaks, that's permanent, total access.
  • A raw key has no scope — it can't say “only this one workspace, read-only.”
  • There's no clean way to revoke it without disrupting the user.

This exact problem — let a third-party app do a limited thing on my behalf without my password, and let me revoke it anytime — is what OAuth was invented for. So we built two layers, in two phases.

Phase 1 — personal access tokens (the simple bearer)

The first, simplest layer: an admin can mint a personal access token (PAT) in the Admin Center — a long random string like iota_mcp_…. It's bound to one member + one workspace, carries scopes, and is revocable. We store only its SHA-256 hash (the raw value is shown once), so a database leak reveals nothing usable.

You paste that token into a generic MCP client and every call is authenticated and tenant-scoped. It's a real, working credential — but it can't power the polished one-click “Add connector” experience that Claude/ChatGPT offer. For that we need real OAuth.

Code: backend/src/auth/mcp_tokens.py, table mcp_tokens (Chapter 3).

Phase 2 — we become an OAuth server

Here's the mental flip worth pausing on. In the Microsoft sign-in flow (Chapter 5), we are the one asking Microsoft to vouch for a user — we are the OAuth client. For MCP it's the mirror image: we are the authority that Claude asks. We play Microsoft's old role. Same protocol, our chair moved to the other side of the table.

Four roles are in play, and naming them makes the diagram readable:

The connect flow, step by step

sequenceDiagram autonumber participant U as User's browser participant C as Claude (the client) participant I as Indigo Iota (auth server) C->>I: discover (.well-known) + register itself (DCR) C-->>U: open /authorize in the browser U->>I: GET /authorize (with a PKCE "challenge") I-->>U: redirect to our /mcp/consent page Note over U,I: user signs in (reusing iota_session)
and picks ONE workspace, clicks Allow U->>I: POST /mcp/consent (Allow + workspace) I-->>U: redirect back to Claude with a one-time code U-->>C: browser hands the code to Claude C->>I: POST /token (code + PKCE "verifier") I-->>C: access token (1h) + refresh token C->>I: POST /mcp (Authorization: Bearer …) → tools run

What each step is defending against

  • Discovery + registration. Claude has never met our server, and we can't pre-arrange with every Claude in the world. So we publish standard /.well-known/… metadata it reads, and it registers itself on the fly (“Dynamic Client Registration”). This is why a connector “just works” from a URL.
  • Authorize → consent. Only the user may approve, which means we must know who they are — but Claude must stay out of that. So we bounce the user's browser to our own consent page and reuse the iota_session cookie to identify them. OAuth doesn't replace our login; it sits on top of it. On the page they pick one workspace (we check it's actually theirs) and click Allow.
  • The one-time code + PKCE. The code travels back through the browser's URL, which can leak. So before starting, Claude invents a random secret and sends us only its hash (the “challenge”). At the token step it must present the original secret (the “verifier”); we hash it and check it matches. A thief who grabs the code from a URL doesn't have the verifier, so the code is useless. (Codes are single-use and expire in minutes.)
  • Two tokens. We return a short-lived access token (~1 hour — the key Claude attaches to each call) and a long-lived refresh token (to get a fresh access token without re-bothering the user). A leaked access token is dangerous only briefly; the powerful long-lived one is used rarely. Refreshing rotates both and revokes the old pair, so a stolen refresh token dies the moment the real one is used.
We didn't hand-roll the cryptography. The official MCP SDK provides the protocol machinery — discovery, /authorize, /token, /register, /revoke, and the PKCE + redirect checks. Our code (backend/src/auth/mcp_oauth.py) provides only the storage and the one custom step: authenticate the human and let them pick a workspace.

How a tool call stays in its lane

Once Claude has an access token, every /mcp call carries it. Three things then happen on our side — and they're the same guardrails the website already had, reused:

flowchart TB t_in["POST /mcp with a Bearer token"] t_verify["Look up the token to get the
member and workspace"] t_open["Open ONLY that workspace brain database"] t_run["Run the read tool and return raw facts"] t_in --> t_verify --> t_open --> t_run
  • Tenant scoping. The token says which workspace; we resolve that org's brain database and read only it. One customer's token can never touch another's brain.
  • Read-only scope. A token carries brain:read. There is no credit-spending tool, so a connector simply cannot run up an LLM bill — the calling assistant does all the reasoning on its own side.

Chapter 9

Comprehend, one email at a time

Capture and triage get a clean, in-scope email into the database. Comprehend is the expensive, LLM-bound back half that turns that one email into brain pages, a knowledge graph, and a search index. This chapter follows a single real-shaped email through every agent — with the actual system prompts, so you can see exactly what to tweak.

Think of one analyst reading one email and updating a shared dossier: they translate it if it's foreign, list who and what it mentions, decide which of those are people they already have a file on, then for each one they jot a fact or two, note who it connects to, refresh the one-line summary, and add a dated line to the timeline. Comprehend is that analyst — run by a swarm of small agents.

The example email

Everything below traces this one message. It arrives in German on purpose, so the very first agent — the translator — has real work to do. The workspace already has two seeded anchor pages: Felix Kasiske (a person, marked the principal — the workspace's centre of gravity, known by his address) and Acme (a company).

From: Michael Dempsey <michael.dempsey@acme.com>
To: Felix Kasiske <felix.kasiske@rpx-optimization.com>
Subject: Einführung — Projekt Helios DE
Hallo Felix, ich möchte Dich gern mit Sarah Lindqvist von Northwind Logistics bekannt machen. Sarah leitet dort den Einkauf und ist sehr an unserem Projekt Helios interessiert. Du erreichst sie direkt unter sarah.lindqvist@northwind.io. Viele Grüße Michael Dempsey Acme GmbH

The connector that captured this also handed comprehend the structured header fields it will need later: sender = michael.dempsey@acme.com, sender_name = "Michael Dempsey", and participants = ["michael.dempsey@acme.com", "felix.kasiske@rpx-optimization.com"]. Those drive the deterministic, header-grounded edges at the end.

The shared machinery (every agent)

Each agent below is a thin subclass of Agent (comprehend/agents/base.py). It writes a prompt; the base class does the rest:

  • Model — one call to LLM_BASE_MODEL (the EU open-weights model, openai/gpt-oss-120b on api.llmbase.ai), single user message, no system role.
  • Concurrency cap — a global semaphore (LLM_BASE_MAX_CONCURRENCY, default 4) queues every call across every thread, so the fan-out never trips LLMBase's “too many concurrent requests”.
  • Retries — up to 5 attempts on transient 429/timeout/5xx with exponential backoff + jitter.
  • Hard credit cap — enforce_credit_limit() fires before the call; an over-budget org raises CreditLimitExceeded and the runner stops cleanly.
  • Metering — every response's token counts are costed against the price book and written to llm_usage_events (this is what the per-email trace in Observability sums).
  • Defensive JSON — _call_json() strips ```code fences and falls back to a default on malformed JSON, because cheap models are unreliable.

Stage 0, Translate DE → EN

T TranslatorAgent

Why first: the brain is English-only by policy — every page, edge, chunk and embedding is built from English text. So a non-English body is translated once, here, before any other agent sees it. (Triage already ran upstream on the raw German using a multilingual model, so spam never reaches this paid step.)

Cost gate: we don't translate blindly. looks_german() is a cheap, dependency-free check — any of ä ö ü Ä Ö Ü ß, or ≥3 common German function words (der/die/das/und/ist…). Our email has “möchte”, “Grüße” and “Einführung”, so it trips instantly and the LLM call fires. An English-only customer pays nothing here.

URLs, numbers, and the original line structure. Do NOT add notes,
labels, or commentary. If the text is already English, return it
unchanged. Output ONLY the translated text.

TEXT:
{cleaned}

mit Sarah Lindqvist von Northwind

sarah.lindqvist@northwind.io …

Stage 1, Identify the entities

1 IdentifierAgent

One LLM call lists every entity in the (now English) email, each typed by the tenant's ontology — the types are not hardcoded. Each type's one-line description is fed in so the model knows what counts as a “company” for this customer. It must pick from that closed list and never invent a type. It may attach an email only when the text clearly states that entity's own address.

System prompt (verbatim, comprehend/agents/identifier.py)
IdentifierAgent.run() — type_lines / allowed are filled from the ontology 
List every distinct entity mentioned in the email below that
matches one of the types defined here:

{type_lines}

Return ONLY a JSON list of objects, each with 'type', 'name', and
optionally 'email'. 'type' must be exactly one of: {types}.
Use full canonical names. Include 'email' ONLY when the email text
clearly gives that entity's own address (e.g. a signature, the
From/To line, or 'reach me at …'); otherwise omit it — never guess.
Pick the single best-fitting type for each entity; never invent a
type. No commentary.

Example: [{"type":"{example_key}","name":"Jane Doe","email":"jane@acme.com"}]

EMAIL:
{email_text}

For this tenant {type_lines} expands to: - person: a named individual …, - company: an organisation …, - project: a named initiative or deal …

in
type_lines (ontology) + English email
out — raw mentions (JSON)
[
 {"type":"person","name":"Sarah Lindqvist",
  "email":"sarah.lindqvist@northwind.io"},
 {"type":"company","name":"Northwind Logistics"},
 {"type":"project","name":"Project Helios"},
 {"type":"company","name":"Acme GmbH"},
 {"type":"person","name":"Michael Dempsey"}
]

Python then post-filters: a type not in the allowed set is dropped, and every name runs through clean_person_name() so a stray address can never become a node's display name. Sarah keeps her body-stated address.

This is the highest-leverage prompt for recall. The type definitions live in the ontology (Admin Center → Brain → Ontology), not in code — edit a type's description there to change what gets picked up. Edit the prompt in identifier.py only to change extraction behaviour globally.

Stage 2, Canonicalize onto known entities

2 CanonicalizerAgent no LLM

Despite the name this is deterministic code, not a model call — the cheap LLM was unreliable here and kept splitting “Felix” and “Dr Felix Kasiske” into two pages. It maps each raw mention onto an already-known entity of the same type, by two rules (logic in comprehend/canonicalize.py):

  1. Personal email match (strongest): if the mention's address is a personal one (not info@/noreply@…) and a known entity is known by it, that wins outright.
  2. Name tokens: exact match after lower-casing + honorific strip + umlaut folding, then token-subset either way (“Acme GmbH” ⊇ “Acme”). Most overlap wins; ties break to the longer name.
known anchors (this tenant)
person  Felix Kasiske
        (felix.kasiske@rpx-optimization.com)
company Acme
out — resolved mentions
Sarah Lindqvist     → Sarah Lindqvist  (new)
Northwind Logistics → Northwind Logistics (new)
Project Helios      → Project Helios   (new)
Acme GmbH           → Acme  (token subset → anchor)
Michael Dempsey     → Michael Dempsey  (new)

“Acme GmbH” collapses onto the seeded Acme page instead of spawning a near-duplicate. That single behaviour is why hand-seeding anchors at onboarding matters.

Honorifics, role-inbox addresses, and umlaut folding are all simple lists/functions in canonicalize.py (_HONORIFICS, _ROLE_LOCALPARTS, _UMLAUT_FOLD) — extend those rather than reaching for an LLM.

Stage 2b, Inject the people on the envelope

+ Participant injection + the principal

An email always has a sender and recipients in its headers, even if the body names no one. So before fanning out, the pipeline adds them as person entities (each cleanly named and resolved by address, recipients capped at 8 to survive a mailing list). It also always offers the principal as a relationship target — never re-processed, just a place for edges to land.

This is why every email yields at least the sender + a real entity, and why the graph is never empty even for a one-line note.

Entities entering the fan-out (deduped on type+name)
Michael Dempsey person Felix Kasiske principal Sarah Lindqvist person Acme company Northwind Logistics company Project Helios project

Felix arrives twice — named in the To line and as the seeded principal — and _dedup_entities() merges them into one, carrying the address across.

Per-entity fan-out

Now each entity gets its own brain page, built in parallel (up to 8 entities at once). Within one entity, four agents run concurrently on disjoint parts of the page. We'll follow Sarah Lindqvist — a brand-new person page — through all four. The same four run for Michael, Acme, Northwind and Project Helios simultaneously.

Stage 3, Attributes (the frontmatter)

3 AttributeAgent

One generic agent fills the entity type's configured fields — driven by the ontology's FieldSpec list, not per-type code. It fills a field only if the email states it; anything unstated stays null (or [] for list fields). No guessing.

System prompt (verbatim, comprehend/agents/attribute.py)
AttributeAgent.run() — field_lines / keys come from the type's FieldSpec 
From the email below, extract these facts about the {type_label}
'{name}', if and only if the email clearly states them. For
anything not stated, use null (or [] for list fields). Do not guess.

Fields:
{field_lines}

Return ONLY a JSON object with exactly these keys: {keys}.

EMAIL:
{email_text}
in — for name='Sarah Lindqvist', type_label='person'
Fields:
- role: job title or role, if stated
- organization: the company they belong to
- location: city/country, if stated
out — frontmatter values
{
 "role": "Head of Procurement",
 "organization": "Northwind Logistics",
 "location": null
}

“leads procurement” → role; “from Northwind Logistics” → organization; no city stated → location: null. The email also gave her address, so the page's email field is set from the mention (so future emails resolve to her by address).

Add/rename/redescribe fields in the ontology (Admin → Brain → Ontology). The agent reads them at runtime — no code change needed to capture a new attribute.

Stage 4, Relationships (open inference)

4 RelationshipAgent

Run per subject over the other entities in the same email. The model is free to name the predicate — a short snake_case verb phrase it judges fits — rather than picking from a fixed list. Objects must come from the supplied candidate list exactly as written, so every edge lands on a real, canonical entity (no invented nodes).

System prompt (verbatim, comprehend/agents/relationship.py)
RelationshipAgent.run() — subject + object_lines filled per entity 
The subject is {subj_name} (a {subj_type}). From the email below,
identify the relationships the email DIRECTLY states FROM this
subject TO the other entities listed. For each, choose a SHORT
predicate as a snake_case verb phrase (e.g. works_with, reports_to,
client_of, manages, introduced, mentioned). Reuse the same predicate
for the same kind of relationship — don't invent near-synonyms.

OTHER ENTITIES (possible objects):
{object_lines}

Return ONLY a JSON list of objects, each with 'predicate' (snake_case)
and 'object' (a name from the OTHER ENTITIES list EXACTLY as written).
Only include a relationship the email clearly supports; if there are
none, return []. Never invent an entity.

EMAIL:
{email_text}
in — subject = Sarah Lindqvist (person)
OTHER ENTITIES:
- Michael Dempsey (person)
- Felix Kasiske (person)
- Acme (company)
- Northwind Logistics (company)
- Project Helios (project)
out — raw triples (pre-normalize)
[
 {"predicate":"works_at",
  "object":"Northwind Logistics"},
 {"predicate":"interested_in",
  "object":"Project Helios"}
]

Subject = Michael Dempsey in parallel yields introduced → Sarah Lindqvist, employed_by → Acme, mentioned → Project Helios. “leads procurement” is dropped — procurement isn't an entity.

Open inference maximises recall but risks predicate sprawl — that's what Stage 5 + the per-pair cap contain. To force a closed vocabulary instead, constrain the prompt to a fixed predicate list.

Stage 5, Normalize predicates

5 PredicateNormalizerAgent

Open inference means works_at / works_for / employed_by can all show up meaning the same thing. This agent collapses each new predicate onto the tenant's canonical vocabulary (seeded from predicates already in the graph, grown during the run). It's cheap by design: deterministic snake_case first, an exact registry hit reuses with no LLM call, and an in-process cache means each distinct wording costs at most one call.

System prompt (verbatim, comprehend/agents/predicate_normalizer.py)
PredicateNormalizerAgent.run() — only fires when base ∉ registry and registry ≠ ∅ 
You maintain a canonical vocabulary of relationship predicates
(short snake_case verb phrases). Given a NEW predicate and the
EXISTING canonical predicates, decide:
- If the NEW predicate means essentially the same as one of the
EXISTING ones, return that existing predicate EXACTLY.
- Otherwise return the NEW predicate as a clean snake_case phrase.
Return ONLY the predicate token — no quotes, no explanation.

NEW: {base}

EXISTING:
{known_list}
registry before
communicated_with
employed_by
introduced
mentioned
decisions
works_at      → employed_by   (LLM: synonym)
interested_in → interested_in (new canonical, added)
introduced    → introduced    (exact hit, no LLM)
mentioned     → mentioned     (exact hit, no LLM)

So Sarah's works_at → Northwind Logistics is rewritten to employed_by → Northwind Logistics, and interested_in joins the registry for the rest of the run.

Pre-seed the registry to enforce house vocabulary, or lower the model's freedom by editing this prompt. The hard ceiling on sprawl is the per-pair cap in graph sync (next).

Stage 6, Description (write or update)

6 DescriptionWriterAgent / DescriptionUpdaterAgent

A brand-new page gets a fresh 2–3 sentence summary (writer). An existing page gets the conservative updater: most emails change nothing — routine events belong in the timeline, not the summary — so it defaults to “no change” and only revises on a contradiction or a material change. Sarah is new, so the writer runs.

{email_text}

The updater's conservatism is the whole reason summaries don't churn. If you want richer summaries that absorb every email, loosen its “only revise if…” clause — but expect more cost and drift.

Stage 7, Timeline entry

7 TimelineAgent

One concrete, dated sentence per email per entity. The date is the email's date (header), the sentence is the model's. Exact-duplicate entries are skipped and the list is kept sorted.

EMAIL:
{email_text}

The page that results

The four agents' outputs land on disjoint parts of one JSON object, which is saved to brain_pages (a row in the tenant DB, keyed by persons/sarah-lindqvist.json). This is the source of truth — the graph and search index are derived from it, so a credit-free reinit can always rebuild them from these pages.

Stage 8, Sync to the graph + index

⇄ graph_sync, entities, edges, chunks

After each page saves, sync_page_to_graph() (ingestion/index/graph_sync.py) derives three things:

  • Entity row — find-or-create the subject in entities, stamping its page_path.
  • Relationship rows — each stored triple's object name is canonicalized onto an existing entity (so “Acme GmbH” → Acme again), then written to relationships. A per-pair cap of 3 distinct predicates is enforced durably against what the pair already holds, so no (subject, object) pair ever sprawls.
  • Chunks + embeddings — the description and each timeline entry become one chunk each (frontmatter is not chunked — attribute search belongs in graph queries). Each chunk's text is prefixed with the entity name (and date), embedded with the 1024-dim model, and written to chunks for vector + keyword search.

Finally — back in process_text(), not the LLM — the structural edges are written straight from the header metadata: sender —communicated_with→ each recipient and the principal. These are grounded facts (the envelope), so they're never inferred, and they guarantee ≥1 edge per multi-party email.

What one email cost — and left behind

LLM calls

1 translate, 1 identify, 0 canonicalize, then per-entity (≈4 each × ~5 entities) ≈ 22–32 calls, most in parallel. Costed to llm_usage_events, attributed to the capturing mailbox.

Rows written

5 brain pages, 5 entities, ~7 relationships (incl. 1 structural), ~10 chunks+embeddings, provenance links per row.

Idempotence

Re-running the same email re-asserts the same triples (deduped), replaces the page's chunks, and stamps processed_at so it never re-comprehends twice.

The throughline: the page is the source of truth; entities, edges and chunks are a derived index. Every prompt above is a single user message you can edit in backend/src/ingestion/comprehend/agents/, and every entity type, field, and the seeded anchors are tenant data you change in the Admin Center — no deploy needed.

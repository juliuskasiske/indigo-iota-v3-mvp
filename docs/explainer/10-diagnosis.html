Chapter 10

The diagnosis engine

Chapters 1 to 9 describe how Iota builds a memory of a company. This chapter describes what it now does with that memory: it works out where the company is losing money, and lays the reasoning out as a tree you can argue with.

This is the newest part of the product and the biggest change since the earlier version of this guide. If you read this document a while ago, everything up to Chapter 9 still holds. This chapter is new.

Two layers, and why the difference matters

It helps to hold two ideas apart, because they are easy to confuse.

The context layer is the memory. It reads emails and documents and turns them into organised knowledge: a page for each person, each company, each deal. It does not have an opinion. It only knows things. Chapters 1 to 9 are all about this layer.

The diagnosis layer is the reasoning. It reads that memory and produces an argument: here is where your money is leaking, here is roughly how much, and here is what to do about it. It is opinionated on purpose. This chapter is about this layer.

The context layer is a very good researcher who has read every email in the company and can tell you anything you ask. The diagnosis layer is the consultant who reads the researcher's notes and says "you are giving away 19% in discounts against a 12% policy, and it is costing you about €400,000 a year." One knows facts. The other makes a case.

The words you need

Five terms carry the whole chapter. None of them are technical in a computer-science sense; they come from management consulting.

Objective

What the company is trying to achieve, written down precisely enough to be checked. Not "grow the business" but "grow revenue from €6.2M to €12.4M, as a level we keep earning every year, by the end of 2027." You set this on a screen; the software does not guess it.

Hypothesis

A statement that might be true and can be tested. "We are losing deals because our prices are too high" is a hypothesis. You can go and check it. "Our sales team should try harder" is not — there is nothing to check.

Hypothesis tree

The objective at the top, split into a handful of possible explanations, each of those split again, until the bottom of the tree is a list of specific things somebody could actually do. Drawing the reasoning as a tree is standard practice in consulting, because it makes the shape of an argument visible: you can see what was considered, and what was not.

MECE

Pronounced "mee-see". It stands for Mutually Exclusive, Collectively Exhaustive. It is a test you apply to any split in the tree, and it asks two questions:

  • Mutually exclusive — do the branches overlap? If one branch is "new customers" and another is "enterprise customers", they overlap, because a new customer can be an enterprise customer. You would count the same money twice.
  • Collectively exhaustive — do the branches, together, cover everything? If revenue can only change through price, volume, or mix, then a split into "price" and "volume" has left something out. An answer might be hiding in the part you did not look at.
Think of cutting a cake. Mutually exclusive means no two slices contain the same crumb. Collectively exhaustive means the slices together are the whole cake, with nothing left on the plate.

Initiative

Something a team could start on Monday morning. "Improve pricing" is not an initiative — it is a wish. "Compare our list prices for the top 50 products against three named competitors" is an initiative, because a person could be assigned to it tomorrow and you would know when it was done.

What an "agent" is here

The word agent gets used loosely in the industry, so it is worth pinning down what it means in this codebase, because it is deliberately unglamorous.

An agent is one job, one prompt, one call to the language model. A prompt is just a block of written instructions we send along with the data. Each agent has a narrow task and is required to answer in a fixed format that the code can read.

There is no magic. An agent does not run continuously, does not decide what to do next on its own, and cannot take actions in the world. It is a function that happens to be implemented by asking a language model a carefully-worded question. We use several of them in sequence because a small, well-specified question gets a far better answer than one enormous vague one.

The word "swarm" appears in the code (backend/src/agents/swarm.py) and in the interface. It is historical, and slightly misleading: the agents run one after another, not in parallel and not competitively. Read it as "the group of agents", nothing more.

Written out plainly:

  1. You fill in the objective on the Objectives screen and press save.
  2. The framer compresses it into one sentence. You can read it, edit it, or ask for a new one. This matters because that sentence becomes the root of the tree, so you should agree with it before the software builds an argument on top of it.
  3. The tree starts with that sentence as its only box.
  4. Decomposition splits it into branches. Each branch carries a written reason. Branches can be split again — the software allows two levels of splitting, then stops.
  5. Every bottom branch gets initiatives proposed for it.
  6. Each initiative then goes through four agents in order: validator, planning, sizer, judge. Their combined output becomes the card you see when you click the box.

Where the facts come from

This is the part that keeps the whole thing honest, so it is worth being precise.

Before the agents look at any node, the code searches the company's own memory for material relevant to that specific node. A branch about pricing gets pricing emails. A branch about staff turnover gets different ones. The search combines two methods, which Chapter 1 explains in more depth:

  • Meaning-based search — finds text that means something similar, even when it uses none of the same words.
  • Keyword search — finds text containing the actual words.

Those excerpts are handed to the agent numbered, like a numbered list of exhibits. The agent is told to cite the number of any excerpt it relies on. When it comes back, the code looks up the numbers it cited and attaches the real source to the node. That is why every fact in the interface can show you the document it came from.

Why numbering matters. A language model will sometimes cite a source that does not exist — it will confidently say "excerpt 9" when you only gave it three. Because the code resolves each number against the list it actually sent, an invented citation resolves to nothing and is silently dropped. It cannot become a fake source in the interface. This is checked by a test (test_swarm_parsing.py).

What an initiative card contains

Every box at the bottom of the tree opens into a card with the same five parts. They are always the same five, so two initiatives can be compared fairly.

Alongside those, the card carries a value ("€450k recurring, FY2027"), the reasoning behind that number, a confidence level, whether it can realistically be achieved before the deadline, and the list of facts it stands on.

Why the value is stored as a number

An earlier version of this code asked the model for a display string like "€0.6M (est.)" and stored that. It reads fine and it is nearly useless: you cannot add up strings. To show "we have found €3.2M of a €12.4M target" you have to be able to total the values.

So the sizer is required to return a plain number — 450000, not "€450k" — along with the currency, whether it recurs every year or happens once, and which year it applies to. The interface does the formatting. Two rules protect the total:

  • Initiatives the judge threw out are not counted.
  • A one-off gain is never added into a recurring target. Getting €500,000 once is not the same as earning €500,000 every year, and adding them together would overstate the result. One-off value is reported on its own line.

Steering it: discard and feedback

The software is confidently wrong sometimes. So every box in the tree can be argued with, in two ways.

Discard — "this is wrong"

You reject a box and say why. The box and everything beneath it are marked as discarded. Then the agents propose a replacement, and they are shown three things: the box you rejected, your reason, and the neighbouring boxes the replacement must not overlap with.

The rejected box is kept, not deleted. It stays on the board, struck through. Two reasons: the record of what was considered and rejected is part of the argument, and your reason is the single most useful thing the replacement agent can be told.

Discard is crossing something out in a notebook rather than tearing the page out. You can still see what you rejected, and so can everybody else.

Feedback — "this is close, but…"

You leave a note. The box is rewritten to reflect it, and everything beneath it is rebuilt with your note carried down. So a note on a branch reaches the initiatives underneath it, not just the box you clicked.

Here nothing is marked as discarded, because you were steering rather than rejecting. The old children are replaced quietly. A real example from testing: a branch called "New logo acquisition" was given the note "focus purely on the DACH enterprise segment, no appetite for SMB or self-serve." It came back renamed "DACH enterprise new logo acquisition", with the exclusion written into its reasoning, and half the rebuilt initiatives beneath it named that segment.

One thing you cannot discard

The objective at the root. There is nothing to replace it with — it came from you, not from an agent. If it is wrong, change it on the Objectives screen. You can still leave feedback on it, which re-cuts the whole tree beneath it.

Keeping the cost bounded

Every step above is a paid call to a language model, so the code sets hard ceilings. They live at the top of swarm.py where they are easy to find and change.

LimitValueWhat it stops
Levels of splitting2A tree that keeps dividing forever
Branches per split4A single split fanning out too wide
Branches in total8Total width across the whole tree
Initiatives in total10The most expensive part, four model calls each
Model calls per pass55The backstop, if every other limit is somehow evaded
Model calls per review25Redoing one node must not cost what a whole run costs

Separately, before every single call, the code checks whether the workspace still has credit. If not it stops cleanly and says so, rather than continuing to spend. In an earlier version this check was missing from these agents entirely — a workspace at zero could still run up a bill, and none of that spending appeared in the usage reports.

Honest limitations

Three things are worth knowing before you trust the output.

The MECE test is not enforced, only requested. The decomposition agent is told to produce non-overlapping branches, and usually does. But it can still hand back a split where one branch quietly contains another. Nothing in the code checks this — it needs a human eye, which is part of why discard and feedback exist.

Model quality shows most in two places. Splitting a problem cleanly, and judging whether evidence really supports a number, are the two hardest jobs here. On a cheap model they are the two that visibly suffer. The code allows a different model per agent (LLM_MODEL_DECOMPOSITION, LLM_MODEL_JUDGE) precisely so those two can be upgraded without paying more for the easy steps.

A restart loses work in progress. A running pass lives in the memory of the server process. If the server restarts mid-run, that work is gone and cannot be resumed. On startup the code marks any half-finished run as stopped so the interface does not wait forever for something nobody is doing.

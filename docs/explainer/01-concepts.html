Chapter 1

The concepts, in plain language

Before any diagram makes sense, here are the building-block ideas the rest of the codebase is made of. You know Python; you don't need anything else. Each idea gets a one-paragraph definition and an everyday analogy.

Client & server (and why there are two computers)

A client is the program in front of the user — here, the web browser (Chrome, Safari). A server is a program running on a computer somewhere else that the client talks to over the internet. The client asks; the server answers. They are different programs, often written in different languages, running on different machines.

A client is a customer at a counter; the server is the kitchen behind it. The customer never walks into the kitchen — they hand over an order slip and get a plate back.

Frontend & backend

The frontend is everything that runs in the browser: the layout, buttons, colours, and the code that decides what to show. In this repo that's the frontend/ folder, written in TypeScript with a toolkit called Next.js / React. The backend is the server-side program that holds the real data and does the heavy lifting: backend/, written in Python with a toolkit called FastAPI.

They are deliberately separate. The frontend is "just a face" — it can't be trusted with secrets, because anyone can open the browser and read its code. The backend is the trusted part: it owns the database, the passwords, and the rules about who can do what.

HTTP request & response — and what an "API" is

When the frontend needs something, it sends an HTTP request to the backend: a little message that says "GET me the credit balance" or "POST this new question." The backend sends back an HTTP response, usually a blob of structured text called JSON (just labelled values, like a Python dict). The API ("Application Programming Interface") is simply the menu of requests the backend agrees to answer.

The API is the restaurant's menu. You can order anything on it ("/api/admin/credits", "/api/qa/ask") and you'll get a defined dish back. You cannot order something that isn't on the menu.

Two words you'll see: GET means "just read/fetch something" and POST means "here's some data, do something with it." The text after the address — /api/qa/ask — is the specific menu item, called a route or endpoint.

Database, table, row, column — and SQL

A database is an organised, permanent store of data that survives restarts. This project uses PostgreSQL ("Postgres"). Data lives in tables, which are exactly like spreadsheets: each row is one record (one person, one email), each column is one field of that record (a name, a date). SQL is the language you use to ask the database questions ("give me every person at Acme").

A database is a filing cabinet. A table is one labelled drawer ("People"). A row is one folder in that drawer. A column is one field printed on every folder's cover.

The "brain" — and how Iota stores knowledge

Iota's whole job is to read messy communication and turn it into tidy, structured memory it calls the brain. The brain has three shapes of data:

  • Brain pages — one document per entity (a person, a company, a project). Each has a summary and a dated timeline. Stored as JSONB rows in the database (the page is the source of truth) and indexed into the graph tables from there.
  • Entities & relationships (the graph) — an entity is one thing (a person, company, or project); a relationship is a labelled link between two ("Felix works_at Acme"). Together they form a knowledge graph — a web of dots and connecting lines (which the graph drawing calls nodes and edges).
  • Chunks — the brain pages chopped into bite-sized passages, each turned into a form the computer can search by meaning (see embeddings, next).
A brain page is a Wikipedia article about one person. The graph is the web of blue links between articles. Chunks are individual paragraphs, filed so they can be found later.

Embeddings & "semantic search"

An embedding turns a piece of text into a long list of numbers (a "vector") that captures its meaning. Texts about similar things end up with similar numbers — even if they share no words. That lets the system search by idea, not just by keyword: a search for "who runs the project" can find a sentence about "the engagement lead" even though none of the words match. This project computes embeddings locally (no data leaves the machine) with a small model via a library called fastembed.

Imagine every sentence gets pinned onto a giant map where related ideas sit near each other. "Semantic search" is just looking at what's pinned nearby, instead of hunting for an exact word.

LLM & "RAG" (how the answer is written)

An LLM ("large language model") is the kind of AI that writes fluent text — like the one you're reading now. Iota uses one hosted in the EU, reached through an OpenAI-compatible service called LLMBase. On its own an LLM doesn't know your data, so Iota uses RAG ("retrieval-augmented generation"): first retrieve the relevant chunks from the brain, then hand them to the LLM and say "answer using only these, and cite them." That's why answers come with sources.

Containers & Docker

A container is a sealed box that holds a program plus everything it needs to run (the right Python version, libraries, settings) so it behaves identically on your laptop and on the production server. Docker is the tool that builds and runs these boxes. This project runs as a few containers: one for the backend, one for the database, one for the web server.

A container is a shipping container: pack the cargo once, and it fits every truck, ship, and crane in the world without repacking.

Environment variables & secrets (the .env files)

Programs need settings that change between your laptop and production — database addresses, secret keys. Hard-coding those into the code is unsafe, so they're kept in environment variables, listed in plain-text .env files that are never shared or committed to version control. A secret is a sensitive one (a password, an API key).

The code is a recipe published in a cookbook; the .env file is the sticky note with your house alarm code. You publish the cookbook; you never publish the sticky note.

Multi-tenancy & the "control plane"

One running system serves many customers. Each customer is a tenant. To keep their data completely separate, Iota gives every tenant its own database ("database-per-tenant"). A separate, shared database — the control plane — holds only the directory information: who the customers are, which database belongs to each, who can log in, and the billing ledger. It holds no actual brain content.

An apartment building. The control plane is the lobby directory and mailroom (who lives where, who has a key). Each tenant's brain database is their own locked apartment — the building manager can route mail, but never sees inside.

Sessions, cookies & single sign-on (SSO)

After you log in, the backend gives your browser a cookie — a small signed token the browser automatically sends back on every later request, proving "I'm still the person who logged in." That ongoing logged-in state is a session. There are two ways to log in: SSO ("single sign-on") lets staff use their existing Microsoft work account (via Microsoft's identity system, Entra ID); or, for customers with no Microsoft, native sign-in — email + password + a 6-digit code from an authenticator app (that second factor is MFA, multi-factor authentication). Either way you end up with the same session cookie.

Tokens & connectors (cookies vs. bearer tokens)

A cookie works because a browser sends it automatically. But a program calling the API on your behalf — like the AI assistants Claude or ChatGPT reading your brain — isn't a browser. It proves itself with a bearer token instead: a secret string it attaches to each request on purpose. To hand a program a limited, revocable token without giving it your password, the web's standard is OAuth — the dance behind the one-click "connector" you'll see in Chapter 7. So: cookie = a person in a browser; bearer token = a program with permission.

Credits & metering

Every AI call costs money. Iota meters each one (counts the tokens, applies a price) and bills it against the customer's prepaid credits. When the credits run out, AI calls are paused automatically so spend can never overshoot. In customer-facing figures, 1 credit = $1.

Agent

This word is used loosely in the industry, so here is exactly what it means in this codebase, because it is deliberately unglamorous.

An agent is one job, one set of written instructions, one call to the language model. Those written instructions are called a prompt: a block of text we send along with the data, telling the model what to do and what shape the answer must take.

An agent does not run continuously. It does not decide by itself what to do next. It cannot act in the world. It is a function that happens to be carried out by asking a language model a carefully-worded question. Iota uses many small agents rather than one big one, because a narrow question gets a much better answer than a broad one.

An agent is a single index card that says "read this email and list every person named in it, one per line". Hand the card and the email to a capable assistant, get a list back. That is the whole idea.

Objective function

The company's goal, written down precisely enough to be checked. Not "grow the business" but "increase revenue from €6.2M to €12.4M, as a level we keep earning every year, by the end of 2027." It also records which levers matter most, in order.

The word function here is borrowed from mathematics, where it means the thing you are trying to make as large as possible. Everything the diagnosis agents do is scored against it.

Recurring vs. one-off value

A distinction that sounds pedantic and is not. Recurring value is a new level the company keeps earning every year — raise prices by 3% and, all else equal, you earn that every year from now on. One-off value happens once — sell a building, collect an overdue invoice.

They cannot be added together. €500,000 once is not the same as €500,000 a year, and a plan that mixes them without saying so overstates itself. Iota records which kind each number is, and never sums one into a target of the other kind.

Hypothesis & the hypothesis tree

A hypothesis is a statement that might be true and can be tested. "We lose deals because our prices are too high" is a hypothesis — you can go and check. "Sales should try harder" is not.

A hypothesis tree puts the goal at the top, splits it into a few possible explanations, splits those again, and ends with specific things a team could do. Drawing the reasoning this way is standard consulting practice, because it makes the shape of an argument visible: you can see what was considered, and what was not.

MECE

Pronounced "mee-see", from Mutually Exclusive, Collectively Exhaustive. It is the test applied to any split in that tree.

  • Mutually exclusive — the branches must not overlap. "New customers" and "enterprise customers" overlap, because a customer can be both, and you would count the same money twice.
  • Collectively exhaustive — together, the branches must cover the whole thing. If revenue can only move through price, volume, or mix, then splitting into just price and volume leaves a place an answer could be hiding.
Cutting a cake. Mutually exclusive means no two slices share a crumb. Collectively exhaustive means the slices together are the whole cake, with nothing left on the plate.

Initiative

Something a team could start on Monday morning. "Improve pricing" is a wish. "Compare our list prices for the top 50 products against three named competitors" is an initiative — a person could be assigned to it tomorrow, and you would know when it was finished.

Human in the loop

A phrase meaning the software does not get the last word. Iota's diagnosis is confidently wrong sometimes, so every box in the tree can be rejected or corrected by a person, and doing so sends the agents back to redo that part with the objection in hand. The point is not that the machine is unreliable and needs a babysitter; it is that judgement about a specific business is the part a person actually has.

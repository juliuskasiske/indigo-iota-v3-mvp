Chapter 5

What actually happens when you click

This is the heart of the guide. Five real journeys, each drawn as a chain of steps and then spelled out function by function — every function the journey touches gets its own numbered line with a sentence saying what it does. Follow the file path and you can open the code and read it.

How to read these pages: each diagram gives you the shape; the numbered list under it is the authoritative play-by-play. A line reads file.py, function() — the file, then the exact function that runs at that step. A dashed arrow in a diagram means "the answer travels back".

Flow A, Signing in

Before you can see any real data you must prove who you are. There are three ways in: the real Microsoft sign-in (customers on Microsoft 365); native sign-in — email + password + an authenticator code (customers with no Microsoft); and a dev shortcut (laptop only, when IOTA_DEV_LOGIN=1). All three end the same way — the backend hands your browser a signed cookie, and every later request carries it.

Step by step

  1. components/admin/sign-in-card.tsx — the user clicks "Sign in"; the browser navigates to the backend login route for the workspace slug.
  2. api/app.py, login() (GET /auth/{slug}/login) — the entry point that begins the Microsoft hand-off for this org.
  3. auth/service.py, get_sso_config() — loads that org's Entra client id/secret and org context from sso_connections.
  4. auth/oidc.py, make_pkce(), new_state(), new_nonce() — mint the PKCE challenge and the anti-replay state/nonce values.
  5. auth/oidc.py, build_authorization_url() — assemble the exact Microsoft URL the browser is sent to.
  6. auth/sessions.py, issue_tx() — stash the state, nonce, and PKCE verifier in a short-lived signed transaction cookie so the callback can trust the round-trip.
  7. Microsoft Entra ID — the user authenticates on Microsoft's own pages (outside our system).
  8. api/app.py, callback() (GET /auth/callback) — receives the authorization code Microsoft redirects back with.
  9. auth/sessions.py, read_tx() — recovers the PKCE verifier and nonce from the transaction cookie.
  10. auth/oidc.py, exchange_code() — swaps the code for ID/access tokens at Microsoft's token endpoint.
  11. auth/oidc.py, validate_id_token() — verifies the token's signature against the JWKS and checks the nonce, rejecting anything tampered or replayed.
  12. auth/service.py, upsert_user_from_claims() — creates or updates the users row from the verified Microsoft claims.
  13. auth/service.py, resolve_role() — looks up the user's role in this org via memberships, deciding what they can see.
  14. auth/sessions.py, issue_session() — writes the signed session cookie that is the user's badge from here on.
  15. api/app.py, dev_login() (POST /auth/dev-login) — the laptop-only shortcut: skips Microsoft entirely and jumps straight to issue_session().
  16. api/app.py, me() (GET /auth/me) — on every later page load, reads the cookie back and confirms who you are.

In one sentence: the browser bounces to Microsoft (or takes the dev shortcut), the backend verifies the result, upserts the user, and writes a signed cookie that is your badge for everything afterwards.

Native sign-in (no Microsoft). Some customers have no Microsoft to delegate to, so the backend must verify identity itself. A password alone is too weak — it gets reused, phished, guessed — so it demands a second factor: a rotating code from an authenticator app (something you have, not just something you know). And so a stolen password leaks nothing on its own, the backend won't even admit the password was right until that second factor is also satisfied — which is why sign-in is two steps. First POST /auth/native/login checks the email + password (argon2id hash) and, if correct, issues only a short-lived “MFA-pending” cookie (auth/challenge.py); a second request then verifies the 6-digit code (auth/totp.py) before the real issue_session() cookie is written. (Passwords are never emailed, because email is not safe storage — onboarding instead sends a single-use link, hashed in auth_tokens, to set one and enrol the authenticator: auth/native_auth.py.) The cookie that comes out is identical to the SSO one, so everything after login is the same.

Flow B, An email becomes knowledge (the whole ingestion process)

The product's core magic, and it runs in the background with no one clicking. This is ingestion end-to-end — its four phases capture → triage → comprehend → index. The first two are cheap and run on a timer; the last two are the metered AI half that turns text into a graph.

Step by step — ① Capture + ② Triage no AI

  1. ingestion/scheduler.py, main() — the timer loop: every IOTA_SYNC_INTERVAL_SECONDS it sweeps each configured mailbox.
  2. scheduler.py, _parse_targets() — turns IOTA_SYNC_TARGETS into a list of (slug, mailbox) pairs, skipping malformed entries.
  3. scheduler.py, _make_fetcher() — returns the live GraphMailClient, or a file replayer when IOTA_SYNC_FROM_FILE is set (offline, credential-free).
  4. scheduler.py, _sync_once() — one pass over one target; opens the tenant connection and never lets a single bad mailbox kill the loop.
  5. ingestion/capture/mail.py, ingest_mailbox() — the connector's chokepoint that runs all of capture + triage for one mailbox.
  6. mail.py, _start_capture_run() — opens a row in capture_runs to log this sweep.
  7. mail.py, _load_delta() — reads the saved Microsoft delta cursor from capture_cursors so only what changed is pulled.
  8. ingestion/capture/graph_client.py, GraphMailClient.fetch() — calls Microsoft Graph and returns the changed messages plus the next delta link.
  9. ingestion/capture/normalize.py, normalize_message() — flattens each Graph message into one standard shape (sender, subject, body, attachments, raw).
  10. mail.py, _apply_removal() — a delta tombstone: if Graph says a message was deleted upstream, drop the matching captured_events row.
  11. ingestion/triage/scope_store.py, get_definitions() — loads this tenant's scope buckets and safety margin from triage_buckets / triage_settings.
  12. ingestion/triage/classify.py, classify() — scores the item against the buckets and decides include or exclude.
  13. mail.py, _insert_captured_event() — writes an INCLUDED item to captured_events, deduped on (source, external_id).
  14. mail.py, _record_exclusion() — writes a content-free triage_exclusions row for a drop (reason + bucket only, never the text).
  15. mail.py, _save_delta() — persists the new delta cursor so the next sweep resumes where this one stopped.
  16. mail.py, _finish_capture_run() — stamps the run's tallies (fetched/included/excluded/…) onto capture_runs.
Microsoft or IMAP. The diagram says “Graph,” but the source is per-mailbox. Each tenant's capture_sources table records, for every mailbox, a provider — Microsoft Graph or plain IMAP — and the scheduler picks the matching client (capture/graph_client.py or capture/imap_client.py). Everything downstream of normalize is identical, so an IMAP customer gets the same brain. Non-English mail (e.g. German) is rendered into English first by comprehend/agents/translator.py, since the brain is kept English-only.

Step by step — ③ Comprehend + ④ Index metered AI

  1. ingestion/runner.py, comprehend_pending() — selects unprocessed captured_events (oldest first) and drives them through the pipeline one at a time.
  2. runner.py, _captured_event_text() — renders a stored row back into the From/Subject/body text the agents expect.
  3. ingestion/comprehend/pipeline.py, ComprehendPipeline.process_text() — the per-item entry: it identifies, canonicalizes, then fans out across the entities found.
  4. comprehend/agents/identifier.py, IdentifierAgent.run() — reads the whole item once and lists the people / companies / projects mentioned.
  5. comprehend/agents/canonicalizer.py, CanonicalizerAgent.run() — merges raw mentions ("Felix", "Felix Kasiske") onto already-known canonical entities so duplicates don't spawn.
  6. pipeline.py, _handle_entity() — for each entity, creates or loads its brain page (runs in a per-entity worker thread).
  7. comprehend/page.py, BrainPage + db/brain_pages.py, load_page() / save_page() — the entity's page (frontmatter + description + timeline), held in memory while the agents fill it, then saved as a JSONB row. This is the source of truth, and it is written first — everything below is derived from it.
  8. pipeline.py, _fill_page() — fans out the four LLM agents below for this one entity, then applies their results to disjoint fields of the page.
  9. comprehend/agents/{person,company,project}.py — the frontmatter agent pulls structured fields for the entity's type.
  10. comprehend/agents/judgment.py, RelationshipClassifier / StatusClassifier — judges the relationship (person/company) or project status — interpretation, not fact-pulling.
  11. comprehend/agents/description.py, DescriptionWriterAgent / DescriptionUpdaterAgent — writes a fresh description or merges new facts into the existing one.
  12. comprehend/agents/timeline.py, TimelineAgent.run() — extracts a dated timeline entry for the item.
  13. pipeline.py, _persist() — saves the page first (the source of truth, written even if the next step is off), then derives the graph from it.
  14. ingestion/index/graph_sync.py, sync_page_to_graph() — turns the saved page into graph rows: its own entity plus every outgoing relationship.
  15. db/entities.py, resolve_entity() + db/relationships.py, add_relationship() — the actual writes to entities and relationships (idempotent: a page's old relationships are deleted first).
  16. comprehend/canonicalize.py, canonicalize_or_keep() — collapses a free-text reference ("RPX Optimization GmbH") onto the canonical entity before the relationship is written.
  17. graph_sync.py, _sync_chunks() — (re)builds this page's searchable passages.
  18. index/chunker.py, chunk_page() + index/embeddings.py, embed() — splits the page into sections and computes a local meaning-vector for each (fastembed, free).
  19. db/chunks.py, insert_chunks() — writes the passages + vectors + keyword index to chunks.
  20. runner.py, _record_metadata() — writes the comprehension_log receipt: entities found/created/updated and the measured token + call cost for this item.
  21. runner.py, _record_provenance() — records which brain pages this event created/updated (comprehension_pages — the source-of-truth link, written even if graph sync was off), plus the derived entities and relationships it touched.
  22. runner.py, _mark_processed() — stamps captured_events.processed_at so the item is never comprehended twice.
  23. comprehend/agents/base.py, Agent._call() → billing/metering.py, enforce_credit_limit() + record_safe() — every agent call first checks the org still has credits (stopping the batch cleanly if not), then records the call's cost.

In one sentence: a timer captures changed mail and triages it into captured_events; then, on its own metered cadence, a chain of AI agents comprehends each event into brain pages, writes the entity + relationship graph, chunks and embeds it for search, logs a receipt, and meters every call — pausing cleanly if credits run out.

Flow C, Asking a question (the live Ask page)

The journey behind the cited answer on the Ask page. It's "RAG": retrieve the relevant brain pieces first, then ask the AI to write an answer using only those, with citations.

Step by step

  1. app/ask/page.tsx — the user types a question and submits.
  2. lib/api.ts, ask() — POSTs the question to the backend with the session cookie.
  3. api/app.py, qa_ask() (POST /api/qa/ask) — resolves which tenant brain to open and sets the billing context for the caller's org.
  4. billing/metering.py, set_current_org() — attributes every LLM call in this request to the caller's org, so the right workspace is billed and credit-checked.
  5. qa.py, ask() — the RAG orchestrator that runs retrieval then synthesis.
  6. index/embeddings.py, embed_one() — turns the question into a meaning-vector locally (no AI spend).
  7. db/chunks.py, hybrid_search() — finds the top-K chunks by combined vector + keyword score.
  8. qa.py, _expand_via_graph() — walks one hop out over relationships from the matched entities and pulls each neighbor's description chunk as extra context.
  9. qa.py, _merge_sources() — assembles the citable source list (vector hits first, graph neighbors appended, de-duplicated).
  10. qa.py, AnswerAgent.run() — sends question + sources to the EU-hosted model, instructed to answer using only those and to cite each fact with [N] (request_kind = qa).
  11. agents/base.py, Agent._call() → billing/metering.py — credit-checks then meters the synthesis tokens.
  12. db/questions.py, save_question() — logs the question, answer, and frozen citations to questions so it can be replayed without re-paying.
  13. lib/api.ts → app/ask/page.tsx — the answer + sources travel back and render as prose with numbered citations.

In one sentence: your question is embedded and matched against the brain's chunks, connected entities are pulled in over the graph, the EU model writes a cited answer from only those sources, the cost is metered, the exchange is logged, and the answer returns with its sources.

Flow E, Credits & billing (money in, money out)

Two opposite movements share one ledger. Money in: an admin adds credits. Money out: every AI call deducts its metered cost. A hard check pauses AI work if the balance is exhausted, so spend can never overshoot by more than one in-flight call.

Step by step

  1. components/admin/credits-panel.tsx — an admin enters an amount and clicks "Add credits".
  2. lib/api.ts, addCredits() — POSTs the (customer-facing) amount to the backend.
  3. api/app.py, admin_add_credits() (POST /api/admin/credits/add) — the admin-only route; divides the customer figure back to raw units before storing.
  4. billing/metering.py, grant_credits() — appends a credit_entries row (kind grant/setup/adjustment).
  5. agents/base.py, Agent._call() — the single place every LLM call goes through, for both comprehend and Q&A.
  6. billing/metering.py, enforce_credit_limit() — called before the call fires; raises CreditLimitExceeded if projected spend ≥ granted credits, so a runaway job is paused.
  7. billing/metering.py, _ensure_prices_synced() — picks up any edits to prices.yaml into the dated price history before costing.
  8. billing/metering.py, price_at() — finds the price effective at this call's instant (the greatest effective_from not after now).

  12. billing/metering.py, to_customer_facing() — multiplies raw cost by the markup at the API boundary, so a customer never sees our true cost or which model ran.
  13. components/admin/usage-panel.tsx via lib/api.ts, usage() / credits() — reads the same ledger to draw the balance and spend chart.

In one sentence: top-ups and AI-call costs both write to one control-plane ledger; before any AI work the system checks that ledger and pauses if prepaid credits are used up — and the Admin page reads the same ledger, marked up, to show the balance and spend chart.

Flow F, An objective becomes a diagnosis (the whole run)

This is the newest journey and the one the diagnosis layer exists for. It starts with a person pressing Start and ends with a board full of initiatives, each carrying a number and the facts behind it.

Before reading the diagram, hold three things in mind, because they explain most of the shape.

  • It is a sequence, not a crowd. The word "swarm" is in the product name, but the agents run one after another. Each one is handed what the previous one produced.
  • It writes as it goes. Each box and each field is saved the moment it exists, which is why the board fills in while you watch, and why a run that dies halfway still leaves what it finished.
  • Every AI call is counted first. The credit check happens before the call, not after, so a workspace can never overshoot its prepaid balance.

Step by step

  1. components/steps/agent-swarm-panel.tsx — a person presses Start.
  2. api/app.py, swarm_start() (POST /api/swarm/start) — resolves which customer database to open and, importantly, looks up the org id here and passes it in by hand. The usual trick of stashing it in ambient request state does not survive into a background task, so it is threaded explicitly instead. Without this, a run's spend would be recorded against nobody.
  3. agents/swarm.py, start() — creates the swarm_runs row, copies the current objective into objective_snapshot, and launches the loop in the background. The web request returns immediately; nobody is left waiting on a page.
  4. db/objective.py, get_objective() then describe() — reads the program and turns it into the brief every agent is given.
  5. swarm.py, _frame() — the Framer compresses the program into one sentence, unless a person already wrote or approved one, in which case theirs is used unchanged.
  6. db/hypothesis.py, add_node() — writes the root box. Its evidence is the program itself, so even the root can be opened and shown to have come from somewhere.
  7. swarm.py, _decompose() — the Decomposition agent splits a box into branches that must not overlap and must together cover the whole of it, and writes down both why each branch is worth looking at and why the set is exhaustive. This repeats one level down, widest-first.
  8. swarm.py, _retrieve() → db/chunks.py, hybrid_search() — before any agent judges anything it is handed real passages from the customer's own memory, found by the box's own wording. Each box gets facts about itself. An earlier version gave every box the same opening few thousand characters of the brain, which is the difference between research and decoration.
  9. swarm.py, _initiatives() — the Initiative agent turns each bottom branch into two or three named, concrete things a team could start on.
  10. swarm.py, _validate() — the Validator says which retrieved facts actually support the initiative, and those facts are attached to it.
  11. swarm.py, _plan() — Planning writes what would have to be true for this to be worth doing, and what somebody could do about it this week.
  12. swarm.py, _size() — the Sizer puts a value on it, in the objective's own unit and year, as a number rather than a phrase, plus one sentence defending the arithmetic and a judgement on whether it could realistically land before the deadline.
  13. swarm.py, _judge() — the Judge reads all of the above and returns a verdict (supported, or needs more evidence) and a confidence.
  14. agents/llm.py, call() — every one of those steps goes through here, and every time it checks the credit balance first, then records what the call cost against the workspace, tagged swarm. If the credits run out, the run stops cleanly and says so, rather than failing mysteriously.
  15. swarm.py, _roll_up() — totals what the initiatives are worth against the target, keeping recurring and one-off value apart, and never mixing the two into one number.
  16. GET /api/swarm/tree → steps/hypothesis-canvas.tsx — the browser asks for the tree every few seconds and redraws the board.

In one sentence: the objective is compressed into a sentence, split into non-overlapping branches that each pull their own facts out of the brain, each bottom branch becomes concrete initiatives, and four agents in turn check, plan, size and judge each one — with every AI call credit-checked before it fires and every result written down the moment it exists.

How the cost is kept from running away

A tree that splits four ways, twice, with three initiatives each and five agent calls apiece would be hundreds of AI calls. So the run is bounded twice over, deliberately, in agents/swarm.py:

LimitValueWhat it stops
Branch layers deep2A tree that keeps splitting forever
Branches per split4A split so fine that none of the branches means anything
Branch boxes in total8Width, once depth is capped
Bottom branches that get initiatives5Spreading the initiative budget too thin
Initiatives per branch3Padding out a thin branch
Initiatives in total10A board too big to read
AI calls in one run55Everything else, as a backstop
AI calls per review (Flow G)25A single objection costing as much as a whole run

The first five limits shape the answer; the sixth is the seatbelt. If the shaping limits are ever wrong the last one still stops the bill, and the run finishes with less rather than costing more.

Flow G, Disagreeing with a box

The diagnosis is meant to be argued with, so this flow matters as much as the one above. There are two ways to push back, and the difference between them is not cosmetic.

DiscardFeedback
What you mean"This is wrong.""This is roughly right, but…"
What happens to the boxMarked discarded, and keptRewritten in place
What happens below itEverything under it is marked discarded tooRebuilt with your note in hand

Discarding keeps the old box because a rejected line of reasoning is itself a result. Someone reading the board later should be able to see that the price angle was considered and thrown out, and why. Feedback deletes what was below instead, because the reviewer is steering rather than refusing, and leaving every superseded draft on the wall would bury the board.

Step by step

  1. You open a box on the board and use one of the two review actions at the top of the panel. A reason is required in both cases — a discard without a reason teaches the agents nothing, so the button stays disabled until you write one.
  2. api/app.py (POST /api/swarm/nodes/{id}/discard or /feedback) — writes a node_interventions row marked pending, and starts the work in the background. Your click returns straight away.
  3. agents/swarm.py, intervene() → _run_intervention() — for a discard, marks the box and its descendants discarded and builds a replacement beside it; for feedback, rewrites the box and rebuilds what sits below it. Either way your sentence goes into the prompt, so the agents are told what to avoid or what to fix rather than being asked to try again blindly.
  4. The review row is marked applied and points at whatever the agents produced. The board polls that row — not the run's own running flag — because a review is a small piece of extra work rather than a whole new pass.
  5. The reviewer's words survive independently of the boxes. Migration 0035 exists precisely so that rebuilding a branch cannot erase the discard reasons underneath it.

In one sentence: a written objection is stored, applied to that part of the tree, and fed back into the agents as context for the retry — and it outlives the boxes it was about, so the run's review history reads end to end.

Notice how often the same files reappear — api/app.py is the front door, ingestion/comprehend/pipeline.py is the shared brain-builder, billing/metering.py is the cash register. The next chapter lists every file so none stays a mystery.

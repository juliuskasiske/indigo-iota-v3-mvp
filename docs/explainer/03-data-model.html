Chapter 3

The data model

A piece of email enters as raw text and leaves as a searchable, connected fact. Follow that journey first — the four phases of ingestion — then explore the tables by clicking them in the live diagrams. The detail opens on demand, so nothing here is a wall of text.

Ingestion, in four phases

One process — ingestion — turns a new message into brain. It runs the same way for real email and for the demo seeder, and it splits into four named phases. Each phase has a job and writes specific tables.

Phases ① + ② are the cheap, frequent front half of ingestion — capture + triage, no AI, run on a timer. Phases ③ + ④ are the metered back half — comprehend + index (AI, resumable: it stops cleanly if credits run out). captured_events is the handover point between the two halves.

Three words, three different things

These get confused constantly. They measure three different units — one word each:

WordExactly one…Definition
captured_eventpiece of raw material One communication that passed triage — a single email/file/message, stored verbatim. The input the AI reads.
capture_runsweep of work One pass over a mailbox: "fetched 40, kept 12, dropped 28." The operational log, not the content.
comprehension_logreceipt for one comprehend What phase ③ did with one captured_event — entities found, AI calls, tokens. One per processed event (1:1).

Full provenance, both directions. Every captured_event now records the capture_run_id that first pulled it in (a later sweep that re-sees it counts it as a duplicate and never touches the row, so the id always points at the original sweep). And comprehension_log no longer stops at counts. The primary link is comprehension_pages: the exact brain pages (the source of truth) each comprehend created or updated — recorded the moment the page is written, so it holds even if the graph sync is off. The derived graph-side view follows in two more junction tables: comprehension_entities (with a created/updated action per entity) and comprehension_relationships. "Show every page, entity, and relationship this email touched" is now a plain join. The same trick runs on the read side: question_entities records which entities the brain surfaced for each question and how (a direct vector hit or a 1-hop graph_neighbor), so "what does the brain resurface?" is also a join. capture_cursors still stands alone by design — a cursor is keyed by mailbox.

And the vocabulary itself is now customer-defined. entity_types + entity_type_fields + relationship_types hold the kinds of thing this tenant tracks, the attributes each carries, and the predicates that connect them — each with a one-line description the agents read to drive detection. What used to be hardcoded ("person | company | project" in the agent prompt, "works_at | leads | …" in a frozenset) is now config seeded at onboarding, and entities.type / relationships.predicate are foreign-keyed onto it.

The price book (llm_model_prices) + ledger (llm_usage_events) design is how a bank statement works: each line records the price that applied that day. Re-pricing tomorrow never rewrites yesterday's statement. Live balance is the org_credit_balance view — granted minus spent, computed on demand.

Native sign-in tables (password + authenticator — control plane)

Customers with no Microsoft sign in natively (Chapter 5): email + password + an authenticator app. Four control-plane tables back it, and none keeps a usable secret in the clear — passwords and backup codes are hashed (argon2id), the authenticator (TOTP) seed is encrypted at rest, and invite / reset links are stored only as a hash. Which method an org uses is the organizations.auth_method column ('entra' vs 'native'); SSO customers use none of these because Microsoft holds their credentials.

Connector tables (MCP & OAuth — control plane)

Four more control-plane tables back the MCP doorway (Chapter 7). They hold only bookkeeping — never brain data — and never a usable secret: client secrets are encrypted at rest, and every authorization code or token is stored only as its SHA-256 hash.

erDiagram organizations ||--o{ mcp_tokens : "issued for" users ||--o{ mcp_tokens : "acts as" organizations ||--o{ oauth_tokens : "scoped to" oauth_clients ||--o{ oauth_tokens : "issued to" oauth_clients ||--o{ oauth_auth_codes : "requested by" mcp_tokens { int id PK text token_hash int org_id FK int user_id FK text scopes } oauth_clients { text client_id PK text client_secret_enc text redirect_uris text client_name } oauth_auth_codes { text code PK int user_id FK int org_id FK text code_challenge timestamptz expires_at } oauth_tokens { int id PK text token_hash text kind text grant_id int user_id FK int org_id FK }
  • mcp_tokens — Phase 1 personal access tokens. One row per minted bearer, bound to (member, workspace) with scopes; only the hash is stored, never the raw token.
  • oauth_clients — every Claude / ChatGPT that registered itself (Dynamic Client Registration). Any client secret is encrypted at rest (secret_box).
  • oauth_auth_codes — the one-time, short-lived codes from the consent step, carrying the PKCE challenge and the member + workspace that was approved.
  • oauth_tokens — issued access + refresh tokens (hashed). An access token and its refresh share a grant_id, so revoking either kills the pair.

How the schema stays honest — migrations

Structure changes are numbered SQL files (0001_…, 0002_…), applied in order and recorded once in schema_migrations so they never run twice. backend/src/db/migrate.py brings any database up to the latest version. The rule: never edit an applied file, always add a new numbered one — that's what guarantees every customer's brain has the exact same structure. The table names above are the ones 0006_ingestion_vocabulary.sql settled on: source_events → captured_events, nodes/edges → entities/relationships, and so on.
